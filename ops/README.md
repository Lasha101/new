# ScanID — ops scripts

> **These files were generated by an AI assistant and have never been run
> against your server. Read every line before you use any of them.**
>
> Nothing here was executed against a host, nothing was scheduled, no cron entry
> was installed, no nginx was reloaded, no credential was written. Every value
> that looks like a setting is a placeholder for you to replace. The scripts
> were tested only against a throwaway PostgreSQL created and destroyed inside a
> container — see [Tests](#tests).
>
> ScanID handles identity documents. A mistake in a backup script here is a
> mistake with other people's passports in it. Review accordingly.

---

## What is in here

| File | What it is |
|---|---|
| `backup.sh` | Nightly encrypted PostgreSQL dump, off-site copy, retention pruning. |
| `restore-test.sh` | Restores a backup into a throwaway database and proves it contains data. |
| `nginx-security-headers.conf` | Response headers, including a CSP. **Included** by `deploy/nginx-travelapp.conf`; reaches browsers on the next deploy + nginx reload. |
| `tests/run-ops-tests.sh` | Test suite for the two scripts. Self-contained, local only. |
| `tests/test-nginx-headers.sh` | Validates the snippet parses **and** sends the headers it claims. |

### A note on the paths in this document

**`/opt/travelapp/ops/` is now a real path, not a placeholder.**
`.github/workflows/deploy.yml` rsyncs this directory there on every deploy, so
that is where these scripts actually live on the server. The cron examples below
use it.

Every *other* path is still a **placeholder**: `/etc/scanid/`,
`/var/backups/scanid/`, `/srv/scanid`. None of them was read from your server
and none is created by anything here — substitute consistently, or the cron
entry will point at nothing and fail quietly on the first night.

Note that `--delete` is set on that rsync: `/opt/travelapp/ops/` is a mirror of
this directory, so anything you hand-edit on the server is overwritten by the
next deploy. Change these files in the repository, not on the VPS.

## Before anything else: the three things a human must decide

1. **Where the off-site copy goes.** `backup.sh` will not run without
   `OFFSITE_DEST`. A backup that lives only on the machine it backs up does not
   survive the failure you are actually insuring against.
2. **Where the age private key lives.** Not on the VPS. See below.
3. **Whether HTTPS is working**, before you touch the HSTS line. It is commented
   out for a reason, and the reason is that enabling it early is unrecoverable.

## Prerequisites

On the VPS (for `backup.sh`):

```bash
sudo apt-get install age postgresql-client rsync util-linux
#                    ^encryption  ^pg_dump          ^rsync  ^flock
```

Wherever you run `restore-test.sh` (ideally **not** the VPS — see below):

```bash
sudo apt-get install age postgresql-client
```

`backup.sh` checks for every one of these at startup and names the missing one,
so a missing package fails on the first run rather than silently at 03:17.

### Generate the encryption keypair — off the server

```bash
age-keygen -o scanid-backup.key
# Public key: age1xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
chmod 600 scanid-backup.key
```

- The **public key** (`age1...`) goes on the VPS, in `AGE_RECIPIENT`. It can only
  encrypt.
- The **private key** (`scanid-backup.key`) must never be on the VPS. Store it in
  your password manager *and* one offline copy. Whoever takes the server must
  not also get the ability to read every historical backup.
- `backup.sh` refuses to start if `AGE_RECIPIENT` contains a private key, because
  pasting the wrong half of the pair is the easy mistake here.

**If you lose the private key, every backup is unreadable forever.** There is no
recovery path, no support ticket, nothing. Store it twice, today.

## Configuration

Both scripts read one env file. Create it yourself — it is not in this
repository and must never be committed:

```bash
sudo install -d -m 0750 -o root -g scanid /etc/scanid
sudo install -m 0640 -o root -g scanid /dev/null /etc/scanid/backup.env
sudo -e /etc/scanid/backup.env
```

Override the path with `OPS_ENV_FILE=/some/other/path` if you prefer.

### Variables

Every value below is a placeholder. Replace all of them.

| Variable | Used by | Required | Meaning |
|---|---|---|---|
| `PGHOST` | both | yes | `127.0.0.1`. PostgreSQL should not be on a public interface. |
| `PGPORT` | both | yes | Usually `5432`. |
| `PGUSER` | both | yes | Must be able to read every table. |
| `PGDATABASE` | both | yes | The **production** database name. `restore-test.sh` never writes to it and uses it only to refuse a name collision. |
| `PGPASSWORD` | both | no | Or leave unset and use a `~/.pgpass` at mode 0600, which keeps the password out of the process environment. |
| `BACKUP_DIR` | both | yes | Absolute path, e.g. `/var/backups/scanid`. Create it `0700`. Refused if it is `/`, `/var`, `/etc`, `$HOME` or similar. |
| `AGE_RECIPIENT` | backup | yes | The **public** key, `age1...`. |
| `OFFSITE_DEST` | backup | yes | rsync destination, e.g. `backup@host:/srv/scanid`, or a mounted path. Set to the literal `none` to opt out — it is then reported every night, deliberately. |
| `BACKUP_RETENTION_DAYS` | backup | no | Default `14`. |
| `AGE_IDENTITY_FILE` | restore-test | yes | Path to the **private** key, mode 0600. |
| `RESTORE_PGHOST` / `RESTORE_PGPORT` / `RESTORE_PGUSER` / `RESTORE_PGPASSWORD` | restore-test | no | Restore into a *different* server. Defaults to the `PG*` values. The user needs `CREATEDB`. |
| `SANITY_MIN_ROWS` | restore-test | no | The actual assertion, e.g. `users=1,passports=1,ocr_jobs=0,voyages=0`. Default `users=1,passports=0,ocr_jobs=0,voyages=0`. |

`SANITY_MIN_ROWS` is worth a moment's thought rather than a copy-paste. A
restore that produces four correctly-shaped empty tables succeeds at the
`pg_restore` level and is a total failure in every sense that matters. Set the
minimums to numbers your real database actually exceeds.

## `backup.sh`

```
pg_dump ──pipe──> age ──> /var/backups/scanid/scanid-<UTC>.dump.age
```

The pipe is the point: the unencrypted dump is never a file, not in
`BACKUP_DIR`, not in `/tmp`. Do not "simplify" it into dump-then-encrypt.

What each run does:

1. Refuses to start unless every variable and command is present, `BACKUP_DIR`
   is a sane absolute path, and `AGE_RECIPIENT` is a public key.
2. Takes a `flock`, so two overlapping runs cannot produce two half-files.
3. Dumps and encrypts into `<name>.part`, then renames to the final name only
   once the bytes are complete. A run that dies never leaves something that
   looks like a backup.
4. Rejects a result under 1 KiB — an age file with no payload is about 200 bytes
   of header, so "suspiciously small" means "failed dump".
5. rsyncs it to `OFFSITE_DEST`.
6. Prunes `scanid-*.dump.age` older than `BACKUP_RETENTION_DAYS` — one
   directory, no recursion, only names it wrote itself.
7. Prints exactly one line and exits non-zero if anything failed.

```
2026-09-06T03:17:04Z scanid-backup status=ok duration_s=6 file=/var/backups/scanid/scanid-20260906T031658Z.dump.age bytes=184320 sha256=8f1c… offsite=ok pruned=1 retention_days=14
```

`status=` comes first so a monitor can grep for `status=error` without a parser.

### Test it by hand before you schedule it

Do all four, in order. This is the part people skip.

```bash
# 1. Preflight only — no dump, no upload, no deletion. Shows what it WOULD prune.
sudo -u scanid ops/backup.sh --dry-run

# 2. A real run.
sudo -u scanid ops/backup.sh

# 3. Confirm the file is real, is encrypted, and is not readable.
ls -l /var/backups/scanid/
head -c 21 /var/backups/scanid/scanid-*.dump.age   # -> age-encryption.org/v1
grep -c PGDMP /var/backups/scanid/scanid-*.dump.age # -> 0 (no plaintext dump magic)

# 4. Confirm it arrived off-site, byte for byte.
#    (run from wherever OFFSITE_DEST points)
sha256sum scanid-<stamp>.dump.age   # compare with sha256= in the log line
```

Then — and this is the step that decides whether you have backups at all — run
`restore-test.sh` against that file. See below.

### Scheduling

**No cron entry was installed.** Add it yourself:

```cron
# m h  dom mon dow  command
17 3 * * *  /opt/travelapp/ops/backup.sh >> /var/log/scanid-backup.log 2>&1
```

Then `crontab -l` to confirm. 03:17 rather than 03:00 because every naive cron
in the world fires on the hour.

A systemd timer is strictly better if you are willing: `OnCalendar=03:17` plus
`OnFailure=` a mail unit gives you real failure notification, whereas cron's
depends on a working local MTA that you probably do not have.

Whichever you choose, point something at the exit code — a healthcheck ping, an
`OnFailure=`, a log alert. A backup script nobody watches fails silently for
months and is discovered on the worst possible day.

## `restore-test.sh`

An untested backup is not a backup. This script is what converts one into the
other.

```bash
ops/restore-test.sh --confirm                    # newest backup in BACKUP_DIR
ops/restore-test.sh --confirm --file <path>      # a specific one
ops/restore-test.sh                              # refuses, prints what it would do
```

It decrypts the backup, restores it into `scanid_restoretest_<UTC>_<pid>`, counts
rows in `users`, `passports`, `ocr_jobs` and `voyages`, and drops that database
again — including when the run fails or is interrupted.

**Where to run it.** Preferably not the production VPS. It needs the age private
key, and the whole key model exists to keep that key off the server. Run it on a
workstation, against a PostgreSQL you are willing to write to, with the backup
file fetched **from your off-site destination** — that way you also test the
copy you will actually reach for in an emergency.

**Safety.** It refuses to run without `--confirm`. It never writes to
`PGDATABASE`. The scratch database name is not configurable, always carries the
`scanid_restoretest_` prefix, and is rejected if it equals `PGDATABASE`, if
`PGDATABASE` itself contains that prefix, or if it matches `*prod*`, `*live*`,
`*travelapp*`, `postgres` or a template database.

`pg_restore`'s own exit code is reported but is deliberately not the pass/fail
signal: restoring a `--no-owner` dump into a fresh database emits benign
complaints and exits 1 for them, and a check that cries wolf nightly is a check
that gets ignored. The row counts decide.

**Do this before go-live, and put it in the calendar quarterly.** The failure
mode this catches — backups that ran green for a year and restore to nothing —
is common, and it is only ever discovered by trying.

## `nginx-security-headers.conf`

The security response headers, including the CSP. Applied by the vhost — see
below.

### How to apply it

**This is now wired up — you do not need to add the include yourself.**

`deploy/nginx-travelapp.conf` includes the snippet at server level:

```nginx
server {
    ...
    include /opt/travelapp/ops/nginx-security-headers.conf;
}
```

and `.github/workflows/deploy.yml` rsyncs `ops/` to `/opt/travelapp/ops/`
immediately before it rsyncs `deploy/`, so the include target is always on disk
by the time the vhost referencing it lands.

⚠️ **The include is at server level on purpose.** `add_header` in a nested block
REPLACES every header inherited from the parent instead of merging. None of the
four `location` blocks in the vhost adds a header today; if you ever add one,
repeat the include inside that block or every header here silently stops being
sent for that path.

⚠️ **The deploy fails loudly if the snippet is missing.** `deploy.yml` runs
`nginx -t` and exits non-zero when the config does not parse. That is
deliberate — a missing snippet should stop a deploy, not ship a site with no
security headers. It also means: do not delete `ops/nginx-security-headers.conf`
without first removing the include line.

Then, on the server:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

### How to verify it actually applied

`nginx -t` passing proves only that the file parses. Check the wire:

```bash
curl -sS -D - -o /dev/null https://your-domain/ | grep -Ei \
  'content-security-policy|x-frame-options|x-content-type|referrer-policy|strict-transport'
```

You should see `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`
and a **single-line** `Content-Security-Policy`. No `Strict-Transport-Security`
until you have deliberately enabled it.

Then open the app in a browser with the console visible and exercise it —
log in, upload a document, export a file. Any `Refused to …` message naming a
CSP directive is a directive that needs adjusting. Check on an **iPhone** too:
HEIC upload is the one path this package could not verify.

### Two nginx traps documented in the file itself

- **`add_header` in a `location` block replaces every inherited one, it does not
  merge.** `deploy/nginx-travelapp.conf` has four `location` blocks. Add one
  `add_header` inside any of them and every security header silently stops being
  sent for that path.
- **The CSP must stay on one line.** nginx is not a shell: a trailing backslash
  inside a quoted string is a literal backslash, and the newline stays in the
  value. A multi-line version passes `nginx -t` and then emits a header browsers
  discard — no policy at all, silently. This was not theoretical; it is the bug
  `tests/test-nginx-headers.sh` caught in the first draft of this snippet, which
  is why that test requests a page instead of trusting `nginx -t`.

### About the CSP

Derived from the actual `npm run build` output of this repository, not a
template. `default-src 'self'`, **no Google Fonts origins** (fonts are
self-hosted via `@fontsource`, so no third-party font request exists) and **no
Vision API origin** (Vision is called server-side; the browser never talks to
it). Every non-`'self'` token is justified in a comment next to it.

## Tests

```bash
ops/tests/run-ops-tests.sh        # 94 assertions — backup.sh + restore-test.sh
ops/tests/test-nginx-headers.sh   # 29 assertions — the snippet
```

Both are local and self-contained. `run-ops-tests.sh` builds its own PostgreSQL
cluster in a temp directory on a random loopback port, seeds it with a schema
mirroring `backend/models.py`, and destroys it. It never reads
`/etc/scanid/backup.env` and never contacts a remote host.
`test-nginx-headers.sh` uses a local nginx if there is one and a throwaway
docker container otherwise.

Run them after any change to these scripts.
